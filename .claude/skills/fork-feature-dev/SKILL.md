# 포크 새 기능 개발

규칙과 함정은 레포 루트의 `CLAUDE.md`에 있다. 빌드와 배포 세부는 `fork-sync-deploy` 스킬의 2절과 4절을 따른다.

## 1. 시작 전

1. 두 레포(`~/Codes/obsidian-excalidraw-plugin`, `~/Codes/excalidraw`)에서 다음을 확인한다.
   - `git status`, `git branch --show-current`, `git worktree list`
   - `master`가 `origin/master`보다 뒤처지지 않았는가
2. `docs/fork/README.md`를 읽는다. 만들려는 기능이 기존 포크 기능과 겹치거나 부딪히지 않는지 본다. 같은 영역을 건드리면, 그 기능의 검증 항목이 이번 작업의 회귀 확인 대상이 된다.
3. 업스트림에 이미 비슷한 기능이나 설정이 있는지 찾는다. 대상은 업스트림 코드, 설정 화면, 릴리스 노트다. 설정으로 해결되면 코드를 고치지 않는다.
4. `master`에서 브랜치를 딴다. 플러그인은 `feat/<이름>`이고, 코어도 고친다면 코어에도 같은 이름으로 딴다.

## 2. 어디를 고칠지

- 먼저 플러그인만으로 되는지 본다. 플러그인 코드, `styles.css`, 볼트 설정으로 해결되면 거기서 끝낸다.
  - 예: Option+드래그 텍스트 선택은 코어의 `pointer-events`와 z-index 구조를 CSS 클래스 하나로 덮어서 해결했다.
- 코어는 캔버스 렌더링, hit-test, 요소 모델, 키 처리 같은 엔진 내부를 바꿔야 할 때만 고친다.
  - 예: 임베드 위에 주석 그리기, 비라틴 키보드 단축키.
- 코어를 고치면 업스트림을 반영할 때마다 두 레포를 맞춰야 한다. 이 비용을 사용자에게 알린다.

## 3. 구현 원칙

- 새 로직은 새 파일에 둔다. 업스트림 파일에는 호출 한 줄, 클래스 토글 같은 연결 지점만 넣는다.
- 업스트림 코드를 옮기거나 리포매팅하지 않는다. diff가 작을수록 업스트림 머지 때 충돌이 적다.
- 이미 있는 리스너나 상태가 있으면 새로 만들지 않고 재사용한다. 예: `ExcalidrawView`의 keydown/keyup/blur 핸들러.
- CSS는 `styles.css` 끝에 주석 달린 블록으로 추가한다. 파일을 Python 텍스트 모드로 다시 쓰지 않는다(CRLF가 섞여 있다).
- 업스트림 `AGENTS.md`와 `CODING_STANDARDS.md`를 따른다. register 헬퍼로 정리하기, ownerWindow 기준 처리, 팝아웃 창 지원이 해당한다.
- 수정키나 단축키를 쓰는 기능이라면 다음을 따진다.
  - 그 키의 기존 Excalidraw 동작과 Obsidian 동작 중 무엇을 잃는가
  - 브라우저 기본 동작과 부딪히지 않는가
  - 선택지와 그 대가를 사용자에게 보여주고 고르게 한다.

## 4. 확인

1. `node scripts/build-with-engine-fork.mjs`로 빌드한다. `npm run code`와 `test:fast`를 변경 전 결과와 비교한다.
2. 테스트 볼트에 배포하고 확인한다. 요령은 `fork-sync-deploy` 6절에 있다.
   - 새 기능: 스크립트로 확인할 수 있는 부분(hit-test, 상태, DOM, 클래스)을 확인한다. 실제 마우스, IME, 클립보드 조작은 사용자에게 부탁한다.
   - 회귀: 같은 영역을 건드리는 기존 기능의 검증 항목을 README 표에서 골라 다시 확인한다.
3. 사용자가 써보고 괜찮다고 하면 메인 볼트에 배포한다. 배포 전에는 dry run으로 버전을 확인한다.

## 5. 등록과 합치기

1. `docs/fork/README.md`를 갱신한다.
   - "What it adds"에 기능 설명과, 그 기능 때문에 잃는 기존 동작을 적는다.
   - 검증 표에 확인 방법과 결과를 적는다. 직접 확인하지 않은 결과는 `pass`로 쓰지 않는다.
2. 기능 단위로 커밋한다. 코어와 플러그인을 같이 고쳤다면 두 레포에 각각 커밋한다.
3. `master`에 머지한다. 코어를 고쳤다면 코어 `master`에도 머지한다.
4. 진행 중인 다른 `feat/*` 브랜치가 다른 worktree에 있으면 건드리지 않는다. 머지 순서는 사용자에게 알린다.
5. push는 사용자가 요청할 때만 한다(`CLAUDE.md`의 push 절).
